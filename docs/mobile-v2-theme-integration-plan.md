# 移动端财务分析融合版技术方案

## 1. 新目标重新定义

这次的真实目标不是“重写预算报表”，而是：

1. **保留线上已有的预算报表页**
   - 直接作为四大主题里的 `预算`
2. **把 V2 Demo 中的 3 个主题并入同一页**
   - `报销`
   - `人员`
   - `保障`
3. **全程不改现有移动端技术栈**
   - `roadhog2 + React16 + antd-mobile2 + echarts4 + less`

一句话定版：

> 预算页不重写，只做“主题化接入”；新增一个统一的分析页骨架，把线上预算页和 V2 的报销 / 人员 / 保障三套能力融合成一个版本。

---

## 2. 先说核心判断

## 2.1 这次不需要技术栈重构

从当前仓库看，V2 Demo 的页面能力主要是：

- 顶部时间切换
- 横向主题 Tab
- 指标卡
- 柱状图 / 折线图 / 堆叠柱 / 环图 / 横向排行
- AI 解读卡

这些能力 **`React16 + antd-mobile2 + echarts4` 全都能实现**，没有必须依赖新栈的地方。

所以：

- **不需要因为 V2 Demo 就升级到 Vite / React 18+ / Tailwind / ECharts 5**
- 真正要做的是 **页面结构融合 + 数据接口补齐**

## 2.2 这次应该是“融合改造”，不是“整页推倒重写”

推荐策略不是把老预算页删掉重写，而是：

1. 把线上预算页抽成一个 `BudgetTopic` 模块
2. 新增统一外层页面骨架
3. 把 `报销 / 人员 / 保障` 三个主题按同一骨架接入
4. 统一时间筛选、主题切换、加载态、空态和错误态

这样做的好处：

- 风险最小
- 预算页不用重新验证业务口径
- 新增主题可以独立联调
- 后续还能继续扩展更多主题

---

## 3. 推荐页面形态

最终页面建议长成这样：

```text
财务分析
├─ 顶部标题
├─ 时间切换：本年 / 本季 / 本月
├─ 主题 Tab：预算 / 报销 / 人员 / 保障
│
├─ 预算：直接复用线上已有预算报表页内容
├─ 报销：接入 V2 Demo 的报销分析
├─ 人员：接入 V2 Demo 的人员分析
└─ 保障：接入 V2 Demo 的保障分析
```

注意：

- **预算主题默认选中**
- 页面最底部继续预留 `50px` 固定导航空间
- 各主题内容滚动方式保持和现有移动端一致

## 4. 前端实现建议

## 4.1 页面拆分方式

建议前端拆成下面 5 层：

1. `FinancialAnalysisPage`
   - 页面容器
   - 管理当前时间、当前主题
2. `FinancialAnalysisHeader`
   - 标题
   - 时间下拉
3. `FinancialTopicTabs`
   - 预算 / 报销 / 人员 / 保障
4. `FinancialTopicContainer`
   - 根据当前主题渲染对应内容
5. 4 个主题子模块
   - `BudgetTopic`
   - `ReimbursementTopic`
   - `PersonnelTopic`
   - `GuaranteeTopic`

## 4.2 推荐的融合方式

### `BudgetTopic`

直接复用线上已有预算页代码，不重写业务逻辑，只做两件事：

- 把它从原页面里抽成可嵌入组件
- 接受统一的 `period` 参数

### `ReimbursementTopic`

优先复用你们现有“报销分析”能力，如果已有旧版图表，就按 V2 的结构重新排版；如果没有成型组件，再参考 V2 Demo 补齐：

- 指标卡
- 报销金额与笔数趋势
- 报销类别结构
- 高频供应商 TOP5
- 大额报销排行
- AI 解读

### `PersonnelTopic`

按 V2 Demo 实现：

- 核心指标
- 月度人员费用构成
- 重点费用趋势
- 当前周期费用结构
- AI 解读

### `GuaranteeTopic`

按 V2 Demo 实现：

- 核心指标
- 基础保障月度构成
- 单项保障趋势
- 当前周期费用结构
- AI 解读

## 5. 组件与图表层建议

## 5.1 通用组件建议

建议新增一组通用壳组件，供 4 个主题共享：

- `TopicIntroCard`
- `MetricsGrid`
- `MetricCard`
- `ChartSection`
- `InsightCard`
- `RankingList`
- `LoadingBlock`
- `EmptyBlock`
- `ErrorBlock`

这样可以保证 4 个主题样式统一，而不是每个主题单独拼一套。

## 5.2 图表实现建议

建议把图表配置单独拆成 option builder 文件，避免把 ECharts 配置写死在页面里。

推荐按主题拆：

- `budgetChartOptions.js`
- `reimbursementChartOptions.js`
- `personnelChartOptions.js`
- `guaranteeChartOptions.js`

## 5.3 与当前技术栈的适配结论

这次 V2 中要用到的图表能力，`echarts4` 都能覆盖：

- 折线图
- 柱状图
- 堆叠柱状图
- 环形图
- 横向排行条形图

所以图表层没有升级阻塞。

## 6. 数据与接口方案

## 6.1 不推荐的做法

不建议前端一次性自己去拼：

- 预算旧接口
- 报销接口
- 人员接口
- 保障接口

然后前端再自己算结构、占比、排序。

这样会有 3 个问题：

1. 前端逻辑过重
2. 口径不统一
3. 页面切换时请求链路混乱

## 6.2 推荐的接口策略

如果技术栈不变，我更推荐 **“统一页面壳 + 按主题懒加载接口”**。

也就是：

- 页面首次进入只加载：
  - 页面配置
  - 默认主题 `预算`
- 用户切换到 `报销 / 人员 / 保障` 时，再首次请求对应主题数据
- 请求结果前端缓存，避免反复切换重复请求

## 6.3 为什么推荐按主题懒加载

因为这次有一个现实问题：

- `预算` 已经在线上稳定存在
- `人员` 的数据准备最重
- `保障` 的分类规则也需要后端补口径

如果要求后端一次性返回四个主题的完整数据，改造面会更大。  
而按主题加载有两个明显好处：

1. **不影响已有预算页**
2. **新增三个主题可以并行开发、分开联调**

## 7. 推荐的 GraphQL 设计

## 7.1 最推荐的形态

建议用一个统一 Query，带 `topic` 参数。

```graphql
query MobileFinancialTopic(
  $topic: FinancialTopic!
  $period: FinancialPeriod!
  $orgId: ID!
) {
  mobileFinancialTopic(topic: $topic, period: $period, orgId: $orgId) {
    topic
    period
    metrics {
      label
      value
      trend
      trendState
    }
    charts {
      id
      type
      title
      unit
      labels
      series {
        name
        color
        data
      }
      items {
        name
        value
        color
        unit
      }
    }
    rankingList {
      name
      value
      unit
      note
    }
    largeExpenses {
      project
      category
      amount
    }
    insight {
      title
      summary
      bullets
      source
    }
  }
}
```

## 7.2 这个接口形态的好处

1. 前端只维护一套主题加载逻辑
2. 预算可以先走适配器接旧接口
3. 报销 / 人员 / 保障可以逐步接入，不必一次性改造全部后端

## 8. 后端落地建议

## 8.1 建议增加一层“主题适配服务”

建议后端新增一个服务，例如：

- `mobileFinancialTopicService`

这个服务不一定自己算全部数据，但要负责把不同来源的结果整理成统一协议。

### 预算主题

- 直接适配现有线上预算报表接口
- 尽量不改原口径

### 报销主题

- 可复用已有报销分析统计
- 补齐供应商排行、大额报销排行、类别结构等聚合

### 人员主题

- 需要独立预处理链路
- 原始工资、补贴、社保、公积金等数据要先标准化

### 保障主题

- 需要先做费用分类映射
- 例如：水、电、物业、采暖

## 8.2 后端难度排序

按落地难度看，建议这样判断：

1. **报销**
   - 最容易
   - 现有财务系统通常已有足够字段
2. **保障**
   - 中等
   - 关键在分类映射表是否清晰
3. **人员**
   - 最难
   - 关键在附件预处理和明细标准化

这个排序很重要，因为它决定了真实排期。

## 9. 三个新增主题的实现重点

## 9.1 报销主题

### 可直接落地

报销主题是最适合优先实现的，因为当前仓库里已经有现成结构参考，且大部分数据在财务系统里天然存在。

建议输出字段：

- 本期报销金额
- 本期报销笔数
- 平均单笔金额
- TOP 供应商占比
- 月度报销金额趋势
- 月度报销笔数趋势
- 报销类别结构
- 高频供应商 TOP5
- 大额报销排行

### 技术建议

- 复用老图表思路
- 结构按 V2 Demo 排版
- AI 解读先用规则模板，后续再接大模型

## 9.2 人员主题

### 可以做，但必须先补数据基础

人员主题不能只靠现有报销单主表直接拼，因为它高度依赖：

- 工资
- 补贴
- 社保
- 公积金
- 奖金 / 绩效

这些数据往往来自附件或独立导出表。

### 推荐实现方式

增加一条预处理链路：

1. 定时读取工资 / 补贴类附件或标准表
2. 统一转换成标准明细表
3. 再供移动端接口聚合

### 如果当前数据还不完整

建议分两步：

1. 第一版先做“人员费用总额 + 结构占比 + 趋势”
2. 第二版再补更细的人数、人均、部门对比

## 9.3 保障主题

### 可做，但依赖分类字典

保障主题的关键不是图表，而是分类规则。

需要先定义哪些单据属于：

- 水费
- 电费
- 物业费
- 采暖费

推荐后端维护一份分类映射表，按以下字段识别：

- 报销事由
- 预算项目
- 支付对象类别
- 关键字字典

### 技术建议

- 第一版先保证分类稳定
- 不追求过细颗粒度
- 优先把月度构成和单项趋势做准

## 10. 前端页面加载策略

## 10.1 推荐的加载流程

1. 页面进入
2. 默认加载 `预算`
3. 用户切换主题时，再请求该主题数据
4. 请求成功后缓存到页面状态
5. 再次切回已加载主题时不重复请求

## 10.2 推荐的前端状态结构

```ts
{
  activePeriod: "year",
  activeTopic: "budget",
  topicDataMap: {
    budget: {...},
    reimbursement: {...},
    personnel: {...},
    guarantee: {...}
  },
  topicLoadingMap: {
    budget: false,
    reimbursement: false,
    personnel: false,
    guarantee: false
  }
}
```

这样切换体验会比较顺。

## 11. 兼容你现有组件规范的实现建议

你前面强调的组件约束，这次都可以继续保留：

- 需要暴露能力的组件用 `ref + useImperativeHandle`
- 所有组件继承 `className`、`style`
- 受控 / 非受控模式清晰
- 最小依赖原则
- 单一职责原则

建议只在以下组件上暴露 `ref API`：

- `TopicTabs`
- `ChartSection`
- `PeriodSelector`

普通展示卡片不用为了“规范而规范”去加 ref。

## 12. 风险判断

## 12.1 真正的风险不在前端

这次最大的风险不是老技术栈，而是数据准备。

真正的风险点有 3 个：

1. **人员数据是否足够标准化**
2. **保障费用分类规则是否稳定**
3. **预算老接口与新主题接口的口径是否能统一到同一页**

## 12.2 风险优先级

按风险高低排序：

1. 人员
2. 保障
3. 预算融合
4. 报销

---

## 13. 推荐实施顺序

如果目标是尽快出融合版，我建议这样排：

### 第 1 步：先做页面骨架

- 标题
- 时间筛选
- 主题 Tab
- 预算接入

### 第 2 步：接报销主题

- 这是最容易落地的主题
- 最适合先做完整闭环

### 第 3 步：接保障主题

- 先确认分类规则
- 再做趋势和结构图

### 第 4 步：最后接人员主题

- 先确认预处理数据来源
- 再做正式联调

---

## 14. 最终建议

如果你现在要我给研发一个可以直接执行的建议，我会建议这样拍板：

1. **预算页不重写**
   - 直接作为统一财务分析页中的 `预算` 主题
2. **技术栈不变**
   - 老移动端栈足够承接 V2 的三类图表能力
3. **新增统一页面骨架**
   - 时间切换 + 主题 Tab + 主题容器
4. **接口采用“按主题懒加载”**
   - 这是最适合当前阶段的后端改造方式
5. **开发顺序按“报销 -> 保障 -> 人员”推进**
   - 不要三个主题齐头并进

一句话建议：

> 这次最优解不是重构技术栈，而是把“预算”保留下来做成第一个主题，再用统一骨架把 V2 的“报销 / 人员 / 保障”平滑接进来，后端按主题逐步补数据。
