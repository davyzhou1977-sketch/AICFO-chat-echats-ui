# 移动端 AI 报表重构落地方案

## 1. 先说结论

这次移动端报表重构，**不建议现在就做整站技术栈大迁移**。

更适合立即落地上线的方案是：

1. **前端保留现有移动端技术栈**
   - `roadhog2 + React16 + antd-mobile2 + echarts4 + less`
2. **后端新增一个“面向移动端报表”的聚合接口**
   - 不让前端直接拼接原始 GQL 零散字段
3. **GraphQL 增加一个稳定的新 Query**
   - 返回的字段结构直接对应页面 4 个卡片模块
4. **AI 先做“文案增强”，不要让 AI 直接算金额**
   - 金额、占比、完成率、柱状图数据全部由后端确定性计算
   - AI 只负责一句话摘要、异常提示、建议动作

一句话定版：

> V2 Demo 复用“页面结构和表达方式”，老移动端继续用现有栈开发，后端补一个稳定的聚合层，先把报表稳定上线，再考虑技术栈升级。

---

## 2. 为什么不建议现在直接升级前端技术栈

从当前仓库看，V2 Demo 实际使用的是新技术栈：

- `Vite`
- `React 19`
- `TypeScript`
- `Tailwind`
- `ECharts 5`

而你线上移动端的既有约束是：

- `roadhog2`
- `React16`
- `antd-mobile2`
- `echarts4`
- `less`

这两套技术体系差异较大。  
如果现在为了一个报表页同步做框架升级，会额外引入下面几类风险：

- 构建链路变化，联调周期拉长
- 老页面兼容性回归成本高
- 企业微信 / 钉钉内嵌 H5 真机适配要重测
- 组件库、图表库、样式体系需要一起迁移

所以对“尽快上线”最友好的策略是：

- **短期：保留老技术栈，只重构报表页**
- **中期：把这次新报表沉淀为可复用组件，再评估整站升级**

---

## 3. 这次重构的核心目标

目标不是把一张图片“画出来”，而是把它做成一个可持续维护的真实业务页面。

建议把目标拆成 4 件事：

1. **页面稳定还原**
   - 做出和截图一致的 4 个模块：总览、部门完成率、在途预算、标准经费支出
2. **接口稳定可复用**
   - 后端直接返回前端可渲染的数据结构
3. **口径统一**
   - 避免前端自己猜字段含义、自己算完成率
4. **后续可扩展 AI**
   - 先把结构化报表跑通，再逐步增加 AI 摘要和智能提示

---

## 4. 当前现状判断

### 4.1 从现有仓库看到的情况

- V2 Demo 已经证明了“卡片化报表 + ECharts + 轻量 AI 解读”这条思路是可行的
- 当前 `src/services/schoolFinanceV2Service.ts` 仍是 mock 数据驱动
- 当前 Web 侧已经有一套 AI 报表接口设计思路：
  - `docs/reimbursement-ai-report-api-contract.md`
  - `docs/reimbursement-ai-report-implementation-plan.md`
- 现有移动端 GQL 样例文件 `Data/移动端报表GQL返回的数据.json` 已经有一部分数据基础，但还**不是可直接渲染页面的最终协议**

### 4.2 当前 GQL 样例数据的问题

样例里主要是这种“原始统计字段”：

- `budgetReportData`
- `budgetDepartmentRatio`
- `statApply`
- `statReimburseApplying`
- `MeetingFeeAmount`
- `TrainingFeeAmount`

这些字段的问题不是“没有数据”，而是：

1. **命名不面向页面**
   - 前端无法一眼知道这个字段该放在哪个模块
2. **口径不完整**
   - 比如完成率、图例、排序、单位、进度条最大值等还需要再加工
3. **存在空值和待确认含义**
   - 如 `MeetingFeeAmount`、`TrainingFeeAmount` 为 `null`
4. **与截图结构不是一一对应**
   - 当前样例数据更像“原材料”，不是“可上屏成品”

结论：

> 这次不是前端直接接现有 GQL 原始字段，而是后端或 GQL 层先做一次“报表聚合和口径统一”。

## 5. 推荐的系统架构

### 5.1 架构分工

建议采用下面的职责拆分：

1. **数据服务 / Java 后端**
   - 查询预算、报销、标准经费等原始数据
   - 统一计算金额、占比、完成率、排序
2. **GraphQL 网关**
   - 提供一个面向移动端页面的新 Query
   - 把后端结果包装成稳定协议
3. **移动端 H5**
   - 只负责展示，不负责业务计算
4. **AI 服务**
   - 可选
   - 仅生成摘要和建议，不参与金额计算

### 5.2 为什么这样分

因为这张报表本质上是**管理报表**，不是开放式聊天。

对这种页面，最重要的是：

- 数字要准
- 口径要统一
- 响应要快
- 出错时能降级

所以最稳的方式是：

> 后端负责算数，前端负责展示，AI 负责补充解释。

## 6. 后端改造方案

## 6.1 建议新增一个“移动端报表聚合服务”

不要让页面直接依赖一堆零散统计字段，建议后端新增一个聚合服务，例如：

- `mobileBudgetReportService`

这个服务内部负责：

1. 拉取预算主数据
2. 拉取报销/申请/核销相关统计
3. 拉取部门完成率
4. 拉取标准经费分类数据
5. 统一换算金额和百分比
6. 输出前端可直接使用的结构

## 6.2 后端要承担的计算逻辑

后端统一做下面这些事：

- 总预算计算
- 已核销金额计算
- 在途预算计算
- 实时可用预算计算
- 完成率计算
- 部门完成率排序
- 在途预算各状态金额列表
- 标准经费分类金额、总额、占比
- 空值补零
- 负值和异常值保护

## 6.3 后端必须明确的口径清单

上线前必须由产品、业务、后端一起确认以下口径：

1. **已核销金额**到底取哪张表、哪个状态
2. **在途预算**是否包含申请中、审批中、待核销、追加中等状态
3. **完成率**公式是否为：
   - `已核销金额 / 本年预算总额`
4. **部门完成率**是否允许负值直接展示
   - 当前样例里存在 `-0.47`
5. **标准经费支出**分类口径是否固定为：
   - 差旅费
   - 劳务费
   - 会议费
   - 培训费

如果这 5 个口径不先定，页面很容易出现“图画出来了，但业务不认”的情况。

## 6.4 后端缓存建议

这类报表不建议每次都全量重算。

建议按以下维度做缓存：

- 组织 ID
- 时间范围
- 排序方式

缓存时间建议：

- `5 ~ 15 分钟`

这样可以保证：

- 页面首开速度更快
- 同一时段重复查看更稳定
- 不会因为 AI 摘要重复调用造成性能浪费

## 7. GraphQL 改造方案

## 7.1 不建议继续直接暴露原始零散字段

现有样例更适合内部统计，不适合直接给页面渲染。  
建议保留原接口不动，**新增一个专门给移动端报表页使用的 Query**。

## 7.2 推荐新增 Query

```graphql
query MobileBudgetAiReport($input: MobileBudgetAiReportInput!) {
  mobileBudgetAiReport(input: $input) {
    requestId
    generatedAt
    overview {
      title
      totalBudget
      completedAmount
      inTransitAmount
      availableAmount
      completionRate
      unit
    }
    departmentCompletion {
      sortMode
      unit
      items {
        departmentId
        departmentName
        ratio
      }
    }
    inTransitBudget {
      unit
      maxAmount
      items {
        key
        label
        amount
      }
    }
    standardExpense {
      totalAmount
      highlightLabel
      highlightRate
      unit
      items {
        key
        label
        amount
        color
      }
    }
    aiSummary {
      summary
      source
    }
  }
}
```

## 7.3 输入参数建议

```ts
type MobileBudgetAiReportInput = {
  orgId: string;
  year?: string;
  month?: string;
  sortMode?: "DESC" | "ASC";
};
```

如果当前页面只有“预算报表”一个固定入口，第一版甚至可以先简化为：

- `orgId`
- `year`
- `sortMode`

## 7.4 为什么要新建 Query

因为新 Query 有 3 个明显好处：

1. **前端开发简单**
   - 一个接口拿齐整页数据
2. **后端口径可控**
   - 不需要前端猜业务逻辑
3. **后续扩展方便**
   - AI 摘要、异常标记、导出图片都能继续加

## 8. 前端改造方案

## 8.1 技术栈建议

### 立即上线版

前端建议继续使用现有移动端技术栈：

- `roadhog2`
- `React16`
- `antd-mobile2`
- `echarts4`
- `less`

### 不建议本期引入

- 不建议本期切 `Vite`
- 不建议本期切 `React 18/19`
- 不建议本期切 `Tailwind`
- 不建议本期切 `ECharts 5`

原因很简单：

- 这张页面的图表复杂度不高
- `echarts4` 足够支撑圆环图、柱状图、饼图
- 真正影响上线速度的是接口和口径，不是图表库版本

## 8.2 页面结构建议

页面按 4 个卡片模块实现：

1. **预算总览卡**
   - 标题
   - 总预算金额
   - 圆环完成率
   - 3 个辅助指标
2. **部门完成率卡**
   - 标题
   - 排序按钮
   - 柱状图
3. **在途预算卡**
   - 标题
   - 单位
   - 4 条状态进度
4. **标准经费支出卡**
   - 标题
   - 环形图
   - 图例列表

## 8.3 组件拆分建议

为了符合你给的组件约束，建议拆成下面这些基础组件：

- `ReportSectionCard`
- `BudgetCompletionRing`
- `DepartmentCompletionChart`
- `BudgetStatusProgressList`
- `StandardExpenseDonut`
- `ReportLoading`
- `ReportEmpty`
- `ReportError`

每个组件都遵循以下规则：

- 支持 `className`
- 支持 `style`
- 需要对外暴露方法的组件使用 `ref + useImperativeHandle`
- 可受控则优先支持受控
- 非必须状态在组件内自行维护
- 不额外引入重量级依赖

## 8.4 图表实现建议

本页图表非常固定，建议直接在前端沉淀 3 个 option builder：

- `buildCompletionGaugeOption`
- `buildDepartmentBarOption`
- `buildExpenseDonutOption`

这样做的好处是：

- 页面逻辑和图表配置分离
- 后续换主题色或改单位更快
- 更适合在老项目里维护

## 8.5 样式适配建议

根据你给的约束，页面统一按移动端百分比宽度适配：

- 主内容区域：`padding-bottom: 50px + safe-area`
- 卡片宽度：`100%`
- 卡片间距：统一 `3vw ~ 4vw`
- ECharts 容器高度写死，不用内容撑高

重点注意两件事：

1. **底部固定导航栏**
   - 页面根容器必须预留 `50px`
2. **图表容器高度固定**
   - 否则老端机型容易出现重绘抖动

## 8.6 与 V2 Demo 的复用方式

建议复用的是这 3 类东西：

1. **信息分层**
   - 标题、核心数值、图表、辅助说明
2. **卡片化结构**
   - 每块内容独立，后续易插拔
3. **图表配置思路**
   - 把 option builder 独立出来

不建议直接复用的是：

1. `Tailwind` 类名体系
2. `React 19` 组件写法
3. 当前 Demo 的 UI 组件封装

## 9. “AI”到底放在哪里最合适

这次页面虽然叫“AI 报表”，但第一版最合适的做法不是让 AI 生成整张图。

建议分两层：

### 第一层：确定性报表

由后端稳定返回：

- 金额
- 占比
- 完成率
- 图表数组

### 第二层：AI 文案增强

由 AI 或规则服务生成：

- 一句话摘要
- 简单异常提示
- 建议动作

例如：

- “本年预算完成率偏低，当前主要预算仍沉淀在可用预算池，建议优先关注审批中与待核销环节。”

这样做的好处是：

- 数字不会错
- 页面先能上线
- AI 能力后续可以逐步增强

## 10. 当前样例数据与目标页面的映射建议

下面是基于当前 `Data/移动端报表GQL返回的数据.json` 的落地映射建议。

| 页面模块 | 目标字段 | 当前样例字段 | 建议处理方式 |
| --- | --- | --- | --- |
| 预算总览 | 总预算 | `budgetReportData.totalBudget` | 直接使用，统一金额格式 |
| 预算总览 | 在途预算 | `budgetReportData.totalCashInTransit` 等相关状态字段 | 后端统一汇总，不让前端拼 |
| 预算总览 | 实时可用预算 | `budgetReportData.RealTimeSurplusAvailableBudget` | 直接输出统一命名 |
| 预算总览 | 已核销金额 / 完成率 | 当前样例无法直接可靠判断最终口径 | 必须由后端明确业务口径后计算 |
| 部门完成率 | 部门 + 比例 | `budgetDepartmentRatio[]` | 后端排序、过滤、百分比格式化 |
| 在途预算 | 各状态金额 | `statApply`、`statReimburseApplying`、`statReimburseWaiting` 等 | 后端统一映射成固定 4 个状态 |
| 标准经费支出 | 分类金额 | `MeetingFeeAmount`、`TrainingFeeAmount`、`TravelFeeDetailAmount`、`LaborFeeDetailAmount` | 空值补 0，统一输出分类数组 |

这里最关键的一点是：

> “已核销金额”和“在途预算状态映射”目前不能靠前端猜，必须后端给出最终业务定义。

## 11. 推荐实施排期

如果以“能尽快上线”为目标，建议按两周左右推进。

### 第 1 阶段：口径确认与接口设计（2 天）

- 产品确认 4 个模块最终展示字段
- 后端确认金额口径和状态映射
- GQL 定义新 Query 协议

交付物：

- 接口字段表
- 字段口径表
- 页面静态结构确认稿

### 第 2 阶段：后端聚合开发（3 到 4 天）

- 新增移动端报表聚合服务
- 新增 GraphQL Query
- 接入缓存和空值兜底

交付物：

- 联调环境接口
- 示例返回 JSON

### 第 3 阶段：前端页面开发（3 到 4 天）

- 搭页面骨架
- 接接口
- 做加载、空态、错误态
- 接入排序交互

交付物：

- H5 可运行页面
- 真机联调版

### 第 4 阶段：联调与验收（2 到 3 天）

- 核对金额
- 核对部门排序
- 核对底部导航遮挡
- 核对企业微信 / 钉钉内嵌表现

交付物：

- 验收清单
- 上线版本

## 12. 上线前必须验收的 8 项

1. 总预算、已核销金额、在途预算、实时可用预算四个数字口径一致
2. 完成率和圆环展示一致
3. 部门完成率支持升序 / 降序
4. 空数据时图表不报错
5. `null` 金额按 `0` 展示
6. 页面底部不会被固定导航栏遮挡
7. 真机滚动流畅，切页不闪烁
8. 接口超时或 AI 摘要失败时，报表主体仍能正常展示

---

## 13. 最终建议

如果目标是“马上能开发、尽快上线、风险最低”，我建议你拍板如下：

1. **前端本期不升级框架**
   - 继续用老移动端栈完成本页
2. **后端必须补聚合层**
   - 不要让前端直接消费原始 GQL 统计字段
3. **GraphQL 新增专用 Query**
   - 一次返回整页报表数据
4. **AI 第一版只做摘要**
   - 不参与金额计算
5. **V2 Demo 只复用结构和表达方式**
   - 不直接照搬代码

这样做的结果是：

- 开发量最可控
- 上线风险最低
- 数字最容易对齐业务
- 后续仍然保留整站升级空间

如果后面你们确认要做第二阶段，我建议再单独启动：

- `移动端 H5 技术栈升级项目`

把 `roadhog2 + React16` 逐步升级到新的构建体系，而不是和这次报表重构绑在一起做。
